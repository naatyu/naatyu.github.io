## Corrections and boundaries

“Known beforehand” is not sufficient for an O(n) heap build: bottom-up heapify is. Hash-map operations are expected/average constant under conditions, not a universal O(1) worst case. State bounds are hypotheses, not classifications or judge-specific guarantees. Big-O is an upper bound; expected and amortized analyses are distinguished from worst-case guarantees. Prefix subtraction requires an appropriate aggregate. Window pruning and greedy commitment each need their own proof. Signed values invalidate the usual too-large-sum boundary argument. Static table cell counts are exact, but byte-per-cell assumptions exclude runtime/container overhead.

No empirical runtime, hardware limit or universal “operations per second” was fabricated. The estimator uses exact BigInt arithmetic for integer expressions through n=q=1,000,000, but n log₂ n is explicitly approximate. Small nonzero GB values retain significant digits rather than rounding to zero. Prefix n+q is a growth model, not a CPU instruction count; q=0 may make preprocessing unnecessary.

The decision aid links to related owning mechanisms, not a promise that every advanced candidate has a full implementation at the target section yet. In particular, 0–1 BFS points to the ordered weighted-frontier discussion; Fenwick/segment-tree choice points to additive prefix foundations. Detailed advanced implementations and source-specific production review remain gates. Bit/geometry leaves use complete existing roadmap sources while `algorithms/numbers` is not implemented. No dead planned destination is linked.
