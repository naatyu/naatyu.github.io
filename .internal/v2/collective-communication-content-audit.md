# Collective Communication — authoring review, 2026-10-27

## Editorial decision

Create `training/collective-communication` as an independent reference, explicitly requested and approved by Nathan. Reader question: who sends, who receives, and what does each rank own after each communication pattern? The user requested training examples and especially clear sender/receiver visuals. The new topic owns the operation contracts. `training/parallelism` retains layouts and schedules; `execution/communication` retains implementation, transports and readiness. Added discovery links without removing existing explanations or changing their original publication dates. No legacy routes, recovery sources or preservation decisions changed.

## Content and source scope

Seven original four-rank teaching scenes cover Broadcast, Reduce, AllReduce, AllGather, ReduceScatter, AllToAll and Send/Receive. Each has a static explanation, a concrete training example, named endpoints, an input reference, a partial/result state and an expandable final result for all ranks. Gather, Scatter and Barrier are short related-operation comparisons. SUM is explicit; DDP averaging, unequal-batch weighting, variable MoE counts, microbatch identity and floating-point order are distinguished.

Targeted primary references checked on 2026-10-27: PyTorch distributed reference (operation contracts, variable split sizes, asynchronous completion), PyTorch DDP design (initialization and gradient synchronization), FSDP sharding strategies (gather parameters and reduce-scatter gradients), PyTorch pipeline tutorial (activation/gradient exchanges), and NVIDIA's collective operation definitions (contracts and compositions). Existing Parallelism and MoE sections supply the expert-routing context. This is not a new paper review or library implementation audit. Sources are linked near the relevant claims and collected in the note.

The numeric traces and diagrams are original conceptual examples, not measurements. The simple AllReduce trace uses Reduce then Broadcast. ReduceScatter followed by AllGather is explained independently using [28,32,36,40]; the standalone AllGather deliberately uses unreduced shards [1,6,11,16]. Serial transfer steps make ownership visible and imply no library schedule, network topology or performance ordering.
