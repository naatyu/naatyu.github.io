## Summary

Large-scale RL for LLMs is not just an optimizer problem. It is a distributed systems problem involving separate learner and inference fleets, stale-policy control, rollout orchestration, retry logic, weight transfer, and inference stability.

## Concepts

- **Learner:** the training side that updates weights.
- **Inference fleet:** the serving side that generates rollouts.
- **Staleness:** how far the rollout-generating policy lags behind the learner.
- **Controller:** the process that orchestrates tasks and batches.
- **Weight transfer:** synchronizing learner weights into the inference fleet.

## 1. Why async RL exists

At large scale, rollout generation is expensive and heterogeneous:

- some prompts finish fast
- some use tools
- some require long reasoning traces

Synchronous RL wastes too much hardware waiting for the slowest paths.

So a common design is:

- learner runs continuously
- inference fleet generates rollouts continuously
- a controller manages their interaction asynchronously

## 2. Core architecture

A useful split is:

- **controller**
- **problem workers**
- **rollout workers**
- **router + inference servers**
- **learner**

Typical responsibilities:

- controller: dispatch tasks, collect results, build training batches
- problem worker: manage groups of rollouts for one problem and aggregate rewards
- rollout worker: execute one rollout, possibly with tool use
- inference servers: generate text efficiently
- learner: optimize the policy

## 3. Staleness is a first-class variable

Because inference and learning are decoupled, rollouts are often generated by an older policy.

This creates off-policy mismatch:

- learner has moved
- rollout policy is stale
- importance ratios grow

So the system must explicitly manage:

- how many learner steps happen between inference refreshes
- how stale a rollout is allowed to be before it is discarded

## 4. Inference dominates hardware usage

In many RL programs, inference consumes more hardware than the learner.

Why:

- generation is autoregressive
- long reasoning traces are expensive
- tool-use workloads add latency
- many candidate responses may be needed per prompt

So inference efficiency is not a secondary detail. It is often the main cost driver.

## 5. Numerics gap between learner and inference

This is an underappreciated failure mode.

If learner and inference engines differ in:

- kernels
- precision
- scheduling
- MoE routing behavior

then token probabilities can drift enough to destabilize RL training.

Mitigations include:

- using compatible precision
- replaying MoE routing decisions
- replaying top-p masks
- limiting allowed staleness

## 6. Weight transfer is its own system problem

Refreshing inference weights is not a simple file copy.

Learner and inference may shard tensors differently, use different layouts, or use different precision forms.

So weight transfer often requires:

- resharding
- layout transforms
- dtype transforms
- replication management

At scale, this becomes a repeated distributed synchronization problem rather than a one-time load.

## 6.1 Weight-sync cadence is a stability variable

The learner-to-inference sync interval is not only a throughput parameter.

If syncs are too sparse:

- rollouts become too stale
- importance ratios become less trustworthy
- RL updates become noisier

If syncs are too frequent:

- transfer overhead can dominate
- inference fleets spend too much time reloading or re-quantizing

So sync cadence should be tuned as part of the RL recipe, not treated as fixed plumbing.

## 6.2 Inference precision is part of the RL system contract

Inference fleets may use different precision or quantization settings from the learner for speed reasons.

This can be acceptable, but it should be treated as a controlled numerics mismatch:

- learner runs in one dtype stack
- inference rollouts run in another
- weight transfer may include re-quantization or dtype conversion

The important point is not “they must always match exactly.” It is:

- measure the mismatch
- keep it stable
- and avoid changing it casually during a long RL run

## 7. Reliability patterns

A robust async RL system needs:

- replica watchdogs
- router-level circuit breaking
- rollout retries
- liveness monitoring
- progress watchdogs
- clean restart behavior

The goal is graceful degradation:

- individual inference replica failure should reduce throughput
- not kill the whole RL job

## 8. What this changes about RL engineering

Once RL is asynchronous and distributed, the real object being optimized is not just:

$$
\mathcal{L}_{RL}
$$

It is something closer to:

$$
\text{training progress per wall-clock hour under staleness and failure constraints}
$$

That is why RL infra and RL objective design are tightly coupled.

## 8.1 Exact rollout/runtime equivalence matters more for agentic RL

In single-turn text RL, small rendering differences may be tolerable.

In multi-turn, tool-using, agentic RL they are often not. If rollout rendering differs from production rendering, the model may be trained on a conversation protocol it never sees again after deployment.

So RL infra should preserve:

- tokenization behavior
- assistant-message rendering
- tool-call formatting
- turn-boundary semantics

as first-class invariants.
