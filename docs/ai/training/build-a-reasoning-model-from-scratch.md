## Summary

Sebastian Raschka's *Build a Reasoning Model (From Scratch)* is an implementation-first guide to the complete reasoning-model pipeline. The central lesson is not that one algorithm creates reasoning. A usable reasoning model emerges from a sequence of connected components:

1. start from a pretrained language model,
2. build a trustworthy evaluator,
3. spend additional compute at inference time,
4. train with verifiable rewards,
5. stabilize the reinforcement-learning loop,
6. and distill successful reasoning traces into a cheaper model.

The book's greatest value is showing how these pieces reuse the same primitives. Answer extraction becomes evaluation logic, then a reward function. Token log probabilities begin as confidence scores, then become part of the policy-gradient loss. The same benchmark is used to compare prompting, sampling, reinforcement learning, and distillation.

## Concepts

- **Reasoning model:** operationally, an LLM encouraged or trained to generate intermediate problem-solving tokens before its final answer.
- **Verifier:** a program that extracts, normalizes, and checks an answer against a known solution.
- **Inference-time scaling:** spending more generation compute without changing model weights.
- **Self-consistency:** sampling several independent solutions and selecting the most frequent final answer.
- **Self-refinement:** asking a model to critique and revise a candidate answer iteratively.
- **RLVR:** reinforcement learning whose rewards come from automatically verifiable outcomes.
- **GRPO:** a policy-gradient method that compares multiple responses to the same prompt without training a separate critic.
- **Reasoning distillation:** supervised training on reasoning traces generated by a stronger teacher.

## 1. What "from scratch" means

The book does **not** pretrain a language model from random initialization. It starts from a pretrained open-source Qwen3 model and implements the reasoning machinery directly:

- generation and KV caching,
- answer extraction and verification,
- sampling and voting,
- response scoring and refinement,
- rollout generation,
- rewards and group-relative advantages,
- the policy-gradient loss,
- GRPO stabilization,
- and reasoning-trace distillation.

This is a useful scope. Pretraining creates the model's knowledge and basic capabilities; the book focuses on how post-training and inference procedures elicit, select, and reinforce useful reasoning behavior.

## 2. The end-to-end pipeline

The book can be reduced to the following dependency chain:

| Stage | Input | Main operation | Output |
| --- | --- | --- | --- |
| Base model | Pretrained weights | Autoregressive generation | Candidate solutions |
| Evaluation | Candidate + reference | Extract, normalize, verify | Correctness signal |
| Inference scaling | One prompt | Longer or multiple generations | Better candidate answer |
| RLVR | Prompt + verifier | Sample, reward, update policy | Stronger reasoning policy |
| Stabilization | Training metrics | Clip, regularize, shape rewards | More reliable RL run |
| Distillation | Strong teacher | Generate and imitate traces | Cheaper reasoning model |

The ordering matters. Training before evaluation would make it impossible to tell whether the policy improved. RLVR before a reliable verifier would optimize bugs in the reward pipeline. Distillation before filtering teacher outputs would teach the student the teacher's mistakes.

## 3. Evaluation is the foundation

For mathematical reasoning, comparing raw strings is insufficient. Equivalent answers may differ in spacing, notation, ordering, or algebraic form. The verifier therefore performs a pipeline:

1. generate a full solution,
2. extract the final answer, preferably from a predictable format such as `\boxed{...}`,
3. normalize superficial formatting differences,
4. test exact equality when possible,
5. use symbolic equivalence when exact strings differ,
6. aggregate correctness over a held-out benchmark.

This evaluator has three roles:

- **measurement:** report benchmark accuracy,
- **selection:** compare candidates during inference-time scaling,
- **training:** turn correctness into a reward for RLVR.

This is a deeper point than it first appears: for verifiable domains, the evaluator is not an accessory to the model. It is part of the learning system.

### Keep evaluation and training data separate

The book uses MATH-500 for evaluation and a non-overlapping set of MATH problems for training and distillation. The separation is essential because the verifier is reused throughout the pipeline. If evaluation problems leak into training, every later comparison becomes unreliable.

## 4. Reasoning without changing the weights

The first improvements use additional inference compute.

### Chain-of-thought prompting

Prompting the model to explain the solution step by step extends the generation trajectory. This is the simplest form of sequential test-time compute: the model gets more token positions in which to transform and revise its intermediate state.

It is cheap to implement but not free to run. Longer sequences increase latency and KV-cache usage, and a longer explanation is not automatically a better one.

### Self-consistency

Self-consistency uses parallel test-time compute:

1. sample $N$ diverse solutions using temperature and top-p sampling,
2. extract the final answer from every solution,
3. group equivalent answers,
4. return the majority answer.

The important role of temperature and top-p is to create useful diversity. If every sample is identical, voting adds no information. If sampling is too random, most candidates become incoherent.

The book suggests starting around:

- temperature: $0.5$ to $0.9$,
- top-p: $0.7$ to $0.9$.

These are starting points rather than universal optima. Early stopping is possible once one answer has an unbeatable majority.

### Self-refinement

Self-refinement instead uses sequential feedback:

1. generate an initial answer,
2. ask for a concise critique and repair plan,
3. generate a revised answer,
4. optionally accept the revision only if a scorer prefers it,
5. repeat.

Possible scorers include:

- hand-written format and brevity heuristics,
- the model's average token log probability,
- an external LLM judge or specialized critic.

The book demonstrates an important failure mode: **model confidence is not correctness**. Average log probability can favor a fluent, familiar, confidently wrong answer. On the book's MATH-500 experiments, log-probability-gated refinement was often worse than accepting an unscored revision.

### Empirical trade-off in the book

Selected results from the book's Qwen3/MATH-500 setup illustrate the compute-quality trade-off:

| Method | Model | Accuracy |
| --- | --- | ---: |
| Greedy baseline | Qwen3 0.6B base | 15.2% |
| Chain-of-thought prompt | Qwen3 0.6B base | 40.6% |
| Self-consistency, $N=10$, with CoT | Qwen3 0.6B base | 52.0% |
| Greedy baseline | Qwen3 0.6B reasoning | 48.2% |
| One refinement, heuristic acceptance | Qwen3 0.6B reasoning | 57.8% |

These are not universal rankings. They show that inference-time techniques must be evaluated on the actual model and task. More samples or refinement rounds do not guarantee monotonic gains, while runtime can increase dramatically.

## 5. Training with verifiable rewards

Inference-time scaling changes how an existing policy is used. RLVR changes the policy itself.

For each prompt $x$, GRPO samples a group of responses $y_{1:G}$ and assigns verifier rewards $r_1, \ldots, r_G$. A basic group-relative advantage is:

$$
A_i = \frac{r_i - \mu_r}{\sigma_r + \epsilon}.
$$

Responses that outperform their group get positive advantages; worse responses get negative advantages. The simplified sequence-level policy-gradient loss implemented in the book is:

$$
\mathcal{L}_{\text{PG}}
=
-\frac{1}{G}\sum_{i=1}^{G}
A_i
\sum_{t=1}^{T_i}
\log \pi_\theta(y_{i,t}\mid x,y_{i,<t}).
$$

The negative sign converts reward maximization into the loss minimization expected by the optimizer.

### The minimal GRPO loop

1. Sample several rollouts for the same prompt.
2. Extract and verify each final answer.
3. Convert rewards into relative advantages.
4. Recompute sequence log probabilities with gradients enabled.
5. Form the advantage-weighted policy loss.
6. Backpropagate and update the model.
7. Evaluate checkpoints on a separate benchmark.

This makes the distinction between RLVR and GRPO concrete:

- **RLVR defines the reward source:** an executable verifier.
- **GRPO defines how rewarded rollouts update the policy:** group-relative policy gradients.

### Why groups with uniform rewards teach nothing

If every rollout is correct, or every rollout is wrong, then all group-relative advantages are zero:

$$
r_1 = \cdots = r_G \quad \Rightarrow \quad A_1 = \cdots = A_G = 0.
$$

The loss produces no useful update. The most informative prompts sit near the model's capability frontier, where the group contains both successes and failures. This motivates difficulty filtering and curriculum design in larger RLVR systems.

## 6. The basic objective is not the training recipe

The book's short GRPO run raises Qwen3 0.6B from the 15.2% base-model baseline to 47.4% on MATH-500 after only 50 steps. But training longer can reduce accuracy. This is exactly why the mathematical objective should not be confused with a stable end-to-end algorithm.

### What to monitor

At minimum, track:

- average verifier reward,
- held-out evaluation accuracy,
- response length,
- group advantages,
- policy entropy,
- loss spikes and policy ratios.

Reward alone is insufficient. It can increase because the policy found a reward exploit, while held-out capability deteriorates. Loss magnitude is also hard to interpret in isolation because it depends on the sampled group's reward variation.

### Stabilizers and controls

The book incrementally adds:

- **clipped policy ratios** to limit overly large policy changes,
- **KL regularization** to discourage departure from a reference policy,
- **format rewards** to make reasoning and final answers reliably parseable,
- **entropy tracking** to detect loss of exploration,
- **checkpoint evaluation** to find the useful early-training window.

None is a magic switch. In the book's small experiment, adding a KL term did not prevent eventual collapse. Stabilizers interact with learning rate, rollout count, response length, reward design, and prompt difficulty.

### Format is part of the task

A verifier can only reward what it can extract. Explicit delimiters such as `<think>...</think>` and `\boxed{...}` make intermediate reasoning and final answers easier to separate.

This creates two distinct rewards:

- **outcome reward:** is the answer correct?
- **format reward:** did the model express it through the required interface?

The format reward should support verification, not overpower correctness. Otherwise the model can learn to produce perfect wrappers around wrong answers.

## 7. Distillation is the efficient alternative

RLVR requires online rollout generation during training, often with multiple long responses per prompt. Hard reasoning distillation replaces that loop with a fixed supervised dataset:

1. send training prompts to a strong reasoning teacher,
2. collect its intermediate traces and final answers,
3. verify or filter the generated solutions,
4. format and tokenize the examples,
5. train a smaller student with next-token cross-entropy on the teacher responses,
6. evaluate the student on a held-out benchmark.

The distinction is useful:

| Method | Training target | Exploration during training | Main strength |
| --- | --- | --- | --- |
| RLVR | Scalar verifier reward on student rollouts | Online | Lets the student discover and reinforce its own successful trajectories |
| Distillation | Teacher-generated token sequence | Offline | Transfers useful behavior cheaply and densely |

In the book's setup, a Qwen3 0.6B student distilled from Qwen3 235B-A22B reaches 45.0% on MATH-500, close to the 48.2% Qwen3 0.6B reasoning reference. The same student distilled from DeepSeek-R1 reaches 33.6% after three epochs. Raschka suggests that matching the teacher and student model family may help because tokenizer, prompting conventions, and response style align better.

The practical recipe is often not RLVR **or** distillation, but:

1. use a strong teacher to put reasoning strategies into the student's support,
2. apply RLVR so the student improves trajectories it can generate itself,
3. use inference-time scaling when extra quality justifies extra serving compute.

## 8. Choosing where to spend compute

| Situation | Preferred first tool | Why |
| --- | --- | --- |
| No training budget or weights are inaccessible | CoT, self-consistency, or refinement | Requires inference only |
| Reliable verifier and trainable model | RLVR | Directly optimizes task success |
| Strong teacher but limited online RL infrastructure | Distillation | Converts teacher compute into a reusable student |
| Student rarely obtains any reward | Distillation or SFT before RLVR | Creates initial successful behavior for RL to reinforce |
| Latency matters for most requests | Distill and route reasoning effort | Avoids paying maximum test-time compute every time |
| Answers cannot be checked automatically | Better evaluator or learned judge | Weak reward quality limits selection and training |

The decision is an allocation problem across three compute budgets:

- **teacher/data compute** for synthetic reasoning traces,
- **training compute** for distillation or RLVR,
- **inference compute** for longer traces, multiple samples, or refinement.

## 9. Practical implementation checklist

Before scaling a reasoning experiment:

- Establish a reproducible greedy-decoding baseline.
- Keep train, validation, and benchmark problems disjoint.
- Unit-test answer extraction on malformed and equivalent expressions.
- Log the raw response, extracted answer, reward, and token count together.
- Verify that prompt tokens are excluded from response-only losses where intended.
- Confirm that uniform-reward groups produce zero advantages.
- Track external accuracy rather than trusting reward or training loss alone.
- Sweep inference methods before paying for training; they define useful baselines.
- Filter teacher traces before distillation.
- Save frequent early RL checkpoints because the best model may appear before the final step.
- Treat formatting, stopping behavior, and response length as explicit design choices.

## 10. Limits of the book's recipe

The implementation is intentionally educational:

- The main model is only 0.6B parameters.
- Mathematical answers are unusually easy to verify.
- The simplified GRPO loss is sequence-level and omits much of the infrastructure required by large asynchronous RL systems.
- Benchmark results from one model and random seed should not be treated as universal method rankings.
- Defining reasoning through generated intermediate tokens is operationally useful, but it does not settle whether the model performs symbolic reasoning or sophisticated pattern completion internally.

These limitations do not reduce the book's value. They clarify what it provides: a transparent reference implementation that exposes the mechanics hidden by large post-training frameworks.

## Main takeaway

A reasoning model is not just a pretrained LLM with a longer chain of thought, and it is not just GRPO. It is a coupled system:

$$
\text{model}
+ \text{generation policy}
+ \text{verifier}
+ \text{selection or reward loop}
+ \text{evaluation harness}.
$$

The verifier is the connective tissue. It measures progress, selects inference-time candidates, supplies rewards, and filters distillation data. Once that component is trustworthy, inference scaling, RLVR, and distillation become different ways of spending compute around the same measurable objective.
