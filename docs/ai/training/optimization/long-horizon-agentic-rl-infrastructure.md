## Summary

Long-horizon agent reinforcement learning is a scheduling and state-management problem as much as an optimization problem. Trajectories have highly variable duration, environments may wait through many inference rounds, KV caches grow over time, and the policy can change before a paused trajectory resumes.

Kimi K3's infrastructure addresses these constraints with:

- partial rollouts that prevent the slowest trajectories from blocking an iteration
- suspendable and forkable microVM environments
- an external CPU pool for idle KV-cache prefixes
- colocated rollout and training with aggressive model-state offload
- automatic throttling based on queue and memory pressure

The central idea is to preserve logical trajectory state while releasing scarce GPU and environment resources whenever the trajectory is idle.

## Concepts

- **Rollout straggler:** an unusually slow trajectory that delays the whole synchronized batch.
- **Partial rollout:** trajectory paused before completion and resumed in a later training iteration.
- **Policy staleness:** mismatch between the policy that produced earlier tokens and the updated policy producing later tokens.
- **Environment checkpoint:** serialized execution state that can be resumed without keeping the runtime active.
- **KV-cache write-back:** moving inactive prefix state from GPU to CPU memory and restoring it when generation resumes.
- **Side-effect-free judging:** evaluating a candidate from a forked environment snapshot so grading cannot alter the real trajectory.

## 1. Why long agent trajectories break ordinary RL systems

A short language-model rollout has a relatively predictable cost. An agent rollout alternates between:

$$
\text{model generation}
\leftrightarrow
\text{tool or environment execution}
$$

Its duration depends on:

- number of reasoning steps
- tool latency
- compilation or test time
- failures and retries
- context length
- when the agent decides to stop

In a synchronized rollout batch, total time approaches the slowest sample:

$$
T_{\text{batch}}
\approx
\max_i T_i
$$

Adding more trajectories can therefore reduce utilization by making an extreme straggler more likely.

## 2. Partial rollouts

Suppose a batch contains $N$ prompts with $K$ trajectories each. Instead of waiting for every trajectory, stop the rollout phase when a fraction $\lambda$ is complete:

$$
\frac{\text{completed trajectories}}{NK}
\geq
\lambda
$$

Completed samples enter the training batch. Unfinished samples retain their state and resume in a later iteration.

This changes iteration time from being determined by the tail toward being determined by a chosen quantile:

$$
T_{\text{iteration}}
\approx
Q_\lambda(T)
$$

The benefit is higher and more predictable accelerator utilization.

### The staleness cost

If the policy changes while a trajectory is paused, the complete sequence is generated by multiple policy versions:

$$
\tau
\sim
\pi_{\theta_0},
\pi_{\theta_1},
\ldots
$$

The resumed portion is not strictly on-policy with respect to either the old or new model. Importance ratios or clipped policy updates can tolerate moderate mismatch, but the method assumes updates are local.

Useful monitoring includes:

- age of resumed trajectories in optimizer steps
- per-token importance ratios by age
- divergence between old and current policies
- reward and completion rate by staleness bucket

## 3. Environment suspension

An agent environment can spend most of its lifetime waiting for the next inference response. Keeping a container or VM fully allocated during that time wastes CPU and memory.

A suspendable environment should support:

- fast checkpoint of mutable state
- release of runtime resources while paused
- fast restore before the next tool action
- snapshots for failure recovery
- forks for judging or alternative execution

Kimi's AgentENV uses Firecracker microVMs and incremental dirty-page checkpoints. The report gives `133 ms` checkpoint and `49 ms` resume latency, making suspension practical between agent turns.

### Fork before judging

Some verifiers need to execute commands or modify files. Running them in the agent's live environment can corrupt the final state.

Instead:

$$
s_T
\xrightarrow{\text{fork}}
\begin{cases}
s_T^{agent} & \text{preserved}\\
s_T^{judge} & \text{verification side effects}
\end{cases}
$$

This also supports multiple independent judges and reproducible failure inspection.

## 4. KV-cache lifecycle

Long trajectories accumulate large attention caches, but inactive trajectories do not need their prefixes on GPU.

A tiered design keeps:

- active KV state on GPU
- evicted idle prefixes in CPU DRAM
- model and optimizer state on NVMe when rollout takes over the devices

Only evicted prefixes are written back. This avoids copying active state unnecessarily.

Hybrid-attention models add another complication: fixed-size recurrent states coexist with sequence-growing softmax KV cache. A valid reusable prefix boundary must have both:

- global-attention KV blocks
- a checkpoint for every recurrent-attention state

Sparse recurrent checkpoints save memory but reduce the set of reusable prefix boundaries.

## 5. Colocate rollout and training

Separate rollout and training clusters simplify scheduling but require more GPUs. K3 colocates both phases on a few hundred GPUs.

At phase transitions:

- training weights and optimizer states can be offloaded
- rollout-serving state occupies the accelerators
- reference or teacher weights stay in CPU memory
- teacher computation streams chunks into reusable GPU buffers

This trades transition and offload overhead for higher total hardware utilization.

The relevant metric is not peak throughput in either phase:

$$
\text{useful training progress}
/
\text{total accelerator time}
$$

## 6. Backpressure and automatic throttling

Unbounded rollout admission can exhaust cache memory or overload environments. Fixed concurrency also performs poorly because task lengths vary.

A controller should observe:

- active requests
- queued requests
- GPU KV-cache utilization
- CPU cache-pool utilization
- environment capacity

and adjust admission dynamically.

When memory pressure rises:

$$
\text{admission rate}\downarrow
$$

When queues drain and cache is available:

$$
\text{admission rate}\uparrow
$$

This is ordinary backpressure applied across model serving, RL sampling, and environment execution.

## 7. Verifier isolation

Agentic RL environments must keep the verifier independent from the policy:

- hidden checks must not be readable through tools
- public checks should be diagnostic rather than complete
- the number of submissions can be budgeted
- excessive probing can receive a penalty
- judge execution should occur in a fork or separate environment

The verifier is part of the security boundary. A technically correct reward function is insufficient if its inputs, tests, or state leak into the agent context.

## 8. Practical design checklist

- Measure the full trajectory-duration distribution, not only the mean.
- Choose a completion quantile for partial rollouts and cap trajectory staleness.
- Version policy log-probabilities so resumed samples can be diagnosed.
- Checkpoint environments incrementally and release paused resources.
- Fork environment state before executing invasive judges.
- Tier KV state between GPU and CPU according to activity.
- Keep recurrent-state checkpoints aligned with reusable attention prefixes.
- Apply admission control from queue and cache pressure.
- Include environment failures and restore latency in training metrics.
- Evaluate learning progress per accelerator-hour, not rollout throughput alone.
